# Day 7（2026-09-06）：复盘日——计划书不是越详细越好，它得有预算

## 做了什么

1. 今天不写代码，专门复盘。项目已收尾：41 笔提交、22 个任务全部完成、后端 226 + 前端 128 测试全绿、已推送 GitHub
2. 起因是查一个现象：**执行计划时老是超出上下文、时不时被压缩**。顺着查下去，挖出了计划书的体积账 —— **598 KB / 14,064 行**，其中 **73%（约 10,400 行）是代码块**：java 103 块 5,446 行、vue 26 块 1,995 行、js 36 块 1,665 行、bash 136 块 539 行
3. 找到病根，而且是**明文规定的**：`writing-plans` 技能第 131～139 行的 No Placeholders 一节要求「每个代码步骤必须贴真实代码」「不许写"参照任务 N"，要重复贴一遍」。照着做 22 个任务，等于把整个代码库在计划里提前手抄了一遍
4. 顺带查出三条被忽视的事实：
   - 计划书第 219 行那句「前 7 个已展开，后 15 个**待展开**」，从开工到收尾**一次没改过**，还跟着 `5a184d1` 提交进了 git
   - 项目全部完成后，**201 个勾选框仍然是空的**（只有 10 个勾，且全在手工验收清单里）—— 七天里真正在当账本的一直是 git log
   - 计划书自己写了「组 A/B/C 可并行开工」，但 41 笔提交是一条**严格串行的直线**（任务 7→8→9→10→11 一笔接一笔），并行设计一次没用上
5. 复盘时还翻出一次真实的并发事故：9 月 3 日两个会话同时在跑，一个以为做到任务 17，另一个正在写任务 19 的文件，**双方完全看不见对方**；那个计划文件 3 分钟内长了 14 行
6. 梳理出 23 条心得，归成四个主题：计划书怎么写 / 怎么喂给 AI 执行 / 状态与记忆 / 产品与验证视角。其中 6 条可以升级成硬规矩

## 卡在哪

1. **一开始方案给错了**：我先提的是「把已完成任务归档」这种事后清理，被一句话点醒 ——「就当从没开始过，我发现一开始的计划书也很大」。事后清理对一份**出生就 598 KB** 的文件毫无用处
2. **自己的统计脚本写错了**：第一版 awk 累计逻辑有 bug，算出 java 代码块 38 万行（整个文件才 1.4 万行），差点把错数字写进结论，重算才得到 5,446 行
3. **自己的判断被现实打过脸**：9 月 3 日我先说「做到任务 17」，两分钟后 git 里冒出任务 18 的提交 —— 我依据的是几分钟前的一次只读查询，而仓库一直在动
4. **更深的卡点**：计划书勾选框这套进度机制，七天里没运转过一次。不是忘了勾，是压根没人把它当账本用

## 怎么解开的

1. 方案改成**从源头治**，五条：
   - 计划里**贴测试，不贴实现** —— 测试是规格，实现是答案；答案在计划里存一份、仓库里存一份，必然漂移，而且计划里那份一实现就过期
   - **滚动式分批展开**，一次只展开 3～5 个任务（够一个会话干的量），其余在总览表里留一行摘要
   - **一份计划一个子系统** —— skill 自己的 Scope Check 第 21～23 行就这么要求，这次没执行，四个子系统全塞进了一个文件
   - **体积红线 60 KB / 1,500 行**，超了就拆。有了数字，就不靠「感觉有点大了」
   - 每个任务开头一张 **5 行卡片**（产出文件 / 依赖 / 验收标准 / 要读哪条规则），先读卡片，动手再展开详细步骤
2. 执行侧三条：开工只给「驾驶舱 + 当前任务卡片」，**禁止整份读**；定位只用文本锚点（`grep '^## Task 12:'`）**不记行号**，因为文件在长、行号必漂；并行分组要在计划阶段就写明「用 subagent 并发派发」，否则**标了也会退化成串行**
3. 状态侧的结论：进度**只能有一个地方算数，而且必须落盘** —— 要么提交后同一轮内立刻更新计划书，要么干脆别设勾选框。一份失真的账本比没有账本更危险，它会骗后来的人（包括被压缩过上下文的我自己）
4. 环境类知识一律进 `.qoder/rules/`（每轮自动注入，不花上下文预算）—— Maven 那个死掉的内网镜像 Day 3 踩过、Day 6 又踩了一遍，就是因为知识只留在当天的对话里

## 对 AI 编程助手的认知变化

> （以下是候选稿，按 JOURNAL 的规矩这一节由本人定稿）

- **今天之前我以为**：计划书写得越详细越好，详细等于保险，AI 拿着就能一次做对
- **今天实际感受到的**：详细是有代价的，而且**代价不由写计划的人承担** —— 598 KB 的计划书让执行方时不时被压缩上下文，压缩后连「做到哪了」都要靠猜；而那 73% 的实现代码，在任务完成的那一刻就全部过期，等于抄了两遍还留下一份必然失真的副本。Day 3 我悟到「计划书本身是要被 review 的代码」，今天算补上了后半句：**它还得有预算**，就像代码不能没有体积和复杂度预算一样
- 一句话小结：**计划书写的是「规格和决策」，不是「答案」** —— 把答案留给写代码的人现场产出，计划才不会既撑爆上下文、又立刻过期
