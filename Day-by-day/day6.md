# Day 6（2026-09-05）：录屏验收日——原来选对大模型，比调 prompt 更重要

## 做了什么

1. 准备录屏验收：先写了一版约 2 分钟、按操作动线串起来的口播稿（列表页 → 新建规则 → 一键校验 → 填值运行 → AI 对话 → 收尾）；自己又提炼了一版更短的四点讲法——① 先验证脚本能不能编译通过 ② AI 辅助排查安全漏洞 + 给出更规范的写法 ③ 自动提取占位符让用户填值 ④ 点运行看结果是不是想要的
2. 把大模型从 `qwen-plus` 换成最新的旗舰 `qwen3.8-max`。**发现换模型压根不用改代码**：模型名是个透传的环境变量 `AI_CHAT_MODEL`，全局就 `application.yml` 一处引用，CR 审查和 AI 对话都走它
3. 换之前先 curl 探了一把：`qwen3.8-max` 在公共端点直接返回 200，能调通，**不用换专属端点**；顺带发现它是个「会思考」的模型（返回里带 `reasoning_content`），回答前要先推理一遍，首字更慢
4. 把 `export AI_CHAT_MODEL='qwen3.8-max'` 写进 gitignore 掉的 `tools/local-secret.env`（换模型只留在本机，不进仓库）
5. 重启后端到新模型，`/api/health` 返回 `code:0 UP`，8080 也确认是新进程在占了

## 卡在哪

1. **Maven 又卡在内网 Nexus**：`mvn spring-boot:run` 默认走本机全局 settings 里那个内网镜像（10.246.80.65，当前网络不通），拉不到 parent POM 直接失败——这坑 Day 3 就踩过，今天又忘了先加镜像参数
2. **8080 端口反复「already in use」，但 lsof 又好像查不到**：连着几次启动都报端口占用，可我先前的检查却显示端口是空的，一度以为是「启动竞态」
3. **第一次 kill 是假成功**：我用了 `kill ... 2>/dev/null` 把报错吞了，又拿一个不严谨的 grep 判断端口，得出「已释放」的假结论，差点就信了。直到用完整的 `lsof -i :8080` + `ps` 重查，才发现有一整套**已经跑了一天多的旧后端**（PID 5160 应用 + 5136 mvn）一直占着 8080，跑的还是旧的 `qwen-plus`——我改的配置根本没生效，因为环境变量只在进程启动时读一次
4. **更深层的「卡」**：录屏验收时体感到，同样一套代码和 prompt，`qwen-plus` 给出的 AI 审查 / 对话明显偏「降智」——不是提示词写得不好，是**模型本身的能力天花板就在那**

## 怎么解开的

1. Nexus：复用项目里那份指向阿里云公共镜像的 `tools/tmp-mvn/settings.xml`，所有 mvn 命令带上 `-s` 即可绕开死镜像
2. 端口 / 进程：**不再吞 kill 的报错**，用 `lsof -i :8080`（看全状态）+ `ps` 把真正的占用者揪出来，把 mvn 父进程和它 fork 出来的应用 JVM 一起停掉，再次确认端口空了才重启
3. 换模型：先 curl 验证「模型 + 端点」组合能通，再重启后端——**不盲目重启进一个没验证过的配置**；起来后 health 探活收尾

## 对 AI 编程助手的认知变化

- **今天之前我以为**：AI 输出不够好，是我 prompt 没调到位、代码没喂够上下文，接着抠提示词就行
- **今天实际感受到的**：同一套代码、同一套 prompt，只把 `qwen-plus` 换成 `qwen3.8-max`，AI 审查和对话的质量就明显上一个台阶。模型才是能力的天花板，prompt 调优只是在**逼近**这个天花板；模型本身弱的时候，再抠 prompt 也是边际递减。同时也第一次直观体会到「会思考的模型」的取舍——更聪明，但首字更慢、更烧额度
- 一句话小结：**选对大模型比调 prompt 更重要**——先决定用哪个模型，再谈怎么调；把力气花在选模型上，回报比死磕提示词高得多
